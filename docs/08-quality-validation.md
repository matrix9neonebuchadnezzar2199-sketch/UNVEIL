# 08 — 品質・評価・受入試験計画

## 1. 基本方針

この文書は**将来実装の試験計画**。以下の精度/速度/試験合格をすでに達成したという意味ではない。今回はドキュメント構造・リンク・サンプル記述の整合性を検査するだけで、アプリのE2Eや安全性を実測できる実装はない。

検知、方式特定、解除、意味保存、UI理解、安全性を個別に評価する。成功したファイルだけを分母にせず、未知・未対応・制限到達・失敗も報告する。

## 2. コーパス設計

三層に分ける:

1. **単体fixture:** RFCテストベクトル、自作JS、無害テキスト、正常/破損gzip、境界値。正確な期待bytesを持つ。
2. **校正集合:** 正常なminify済みJS、エンコード済み通常データ、許諾済み配布物、合成難読化、圧縮/画像/暗号化データ等。しきい値を調整する。
3. **固定ホールドアウト:** 校正に使わない未知の生成seed/テンプレート/プロジェクト/版。出荷評価専用。

各試料に `sample_id / sha256 / source / license / generator_version / seed / language / technique_labels / intended_use / expected_assessment / expected_transform_hashes / invalid_or_unsupported / split` を付ける。手作業ラベルは二者レビューし、不一致はinconclusiveとして保持する。

類似試料の漏えいを避け、分割はファイル単位だけでなく元プロジェクト/生成器/テンプレート系列単位。WIKIの公開教材と同一/近重複の試料をホールドアウトから除く。難読化の「意図」は実ファイルだけでは確定できない場合があるため、ラベル根拠と曖昧性を記録する。

暫定最小規模: MVPの方式ごとにホールドアウト陽性100件以上、難しい陰性200件以上、全体の正常ファイル1000件以上。共有する陰性を使う場合も方式別の母数を明記する。危険な実在マルウェアを標準CIへ持ち込まず、自作の無害な構造と異常入力で試験する。

## 3. 指標と暫定出荷基準

| 項目 | 定義 | 暫定基準 |
|---|---|---|
| 難読化兆候precision | TP/(TP+FP)、inconclusiveを陽性に数えない | 全体0.95以上 |
| 難読化兆候recall | TP/(TP+FN)、既知陽性のinconclusiveはFN | 対応方式に限り0.90以上 |
| 正常ファイルFPR | FP/(FP+TN)、陽性でないinconclusiveは別件数にも表示 | 0.02以下、coverageも併記 |
| 方式特定precision/recall | 方式別multi-label。confirmed/probableを選択候補とする | 決定的形式群は各0.95/0.95以上、JS構造兆候は0.90/0.85以上 |
| abstention率 | unknown/inconclusiveの割合 | 制限なし。ただし全体/方式別・支持範囲とともに必須報告 |
| 可逆変換の正確性 | 対応かつ正解既知の出力bytes一致 | 全fixture 100% |
| 意図しないAST変化 | 書換え対象外の前後AST意味要素差異 | fixtureで0件。実行等価性の証明とはしない |
| 原本完全性 | 取込前後/変換後の原本bytes/ハッシュ一致 | 全試験100% |
| 再現性 | 同入力・版・設定で同一出力/同一Finding | 動的時刻等を除き100% |
| 重大安全問題 | 既知Critical/Highの未修正件数 | 0件 |

全precision/recallに母数、混同行列、95% Wilson区間を掲載する。単一スコアだけを宣伝しない。形式検知が合格しても、意図を判定する難読化兆候が合格したとはしない。分母0はN/Aであり100%として扱わない。

しきい値はG00で承認し、G02で実測を見て更新可能だが、ホールドアウトの不合格を隠すために事後変更しない。変更理由と別ホールドアウトでの再評価を要する。未対応ファイルの結果は対応範囲の精度から分離するが、入力総数・未対応率を別に必ず公開する。

## 5. セキュリティ受入試験

| ID | 試験 | 合格条件 |
|---|---|---|
| ST-01 | 実行されるとマーカーを書こうとする無害な入力を各形式で解析 | マーカー未作成。試料由来のexec/子プロセスなし。ワーカー自身の起動は区別 |
| ST-02 | テスト専用侵害想定ワーカーから外部read/write/socket/子起動を試みる | OS制御で全拒否。隔離自己診断失敗時は解析禁止 |
| ST-03 | symlink/ハードリンク/パス偽装/FIFO/取込中変更/書出し競合 | 原本や外部ファイルの変更なし。通常ファイル以外拒否 |
| ST-04 | 圧縮爆弾、深いAST、長い文字列、イベント洪水 | 上限前後で安全停止、UI復帰、全子処理終了、未確定blob掃除 |
| ST-05 | 通信監視、ログ/環境/core dump/キャッシュ/削除の確認 | 試料外送信0、秘密記録0、宣言どおりの保存/削除 |
| ST-06 | HTML/SVG/Markdown/URL/双方向文字を含む試料・記事・レポート | スクリプト/自動通信なし、危険scheme拒否、視覚偽装を可視化 |
| ST-07 | 署名破損パック、不正schema、別Session ID、偽ハッシュ | ブローカー拒否、旧版/既存結果を保持、権限拡大なし |

Fuzzはパーサ/decoder/IPC/差分/Markdownの境界に適用。日次に固定時間とseedで実行し、クラッシュを最小化した回帰fixtureとして追加する。fuzz完走は脆弱性ゼロの証明ではない。

## 6. 性能・安定性

参照環境案: Linux x86_64、4コアCPU、16 GiB RAM、SSD、対象WebView版固定。冷起動/温起動を分け、各代表ケース30回以上、p50/p95/maxとRSSを記録する。

| ID | 試験 | 暫定目標 |
|---|---|---|
| PT-01 | 起動、1 MiB通常JSの取込〜概要、1万記事の索引検索（合成索引） | 初回起動p95 3秒、概要p95 5秒、検索p95 200ms以内 |
| PT-02 | UI操作、中止、同時2ジョブ | UI応答p95 100ms以内、中止後2秒以内に停止、ワーカーRSS各512 MiB内 |
| PT-03 | 50 MiB入力の上限動作、100連続ジョブ、8時間WIKI/解析混合操作 | 予算強制、ハンドル/プロセス漏れ0、回収後RSSの持続的増加なし |

10 MiB AST入力は60秒のジョブ上限内に結果または理由付き部分結果を返す。最大サイズを必ず完全解析できる目標ではない。UI/CoordinatorのRSSは合計300 MiBを暫定予算とし、WebView差をG01で実測して固定する。

性能が厳しい場合は表示/解析範囲を狭める。上限解除や隔離撤廃による高速化は不合格。

## 7. ユーザビリティとデザイン評価

初学者2名・技術者3名以上を目安に、取込→根拠→記事→変換→レポートを観察する。主要タスク成功率90%以上を暫定目標とし、母数とタスク単位を明記する。少人数の値を市場全体の統計と主張しない。

全参加者が「未検出≠安全」「デコード≠暗号解読」「構造検証≠完全等価」を説明できることを理解面のゲートとする。理解できない場合は文言/配置を直して再試験する。見栄えはユーザーの最終UI承認を別途必要とする。

## 8. CI・出荷チェックリスト

PRごと: 文書リンク/schema/型検査/lint/単体fixture/契約/E2E smoke。定期: fuzz/性能/アクセシビリティ/依存安全性。リリース時: 全AT/ST/PT、ホールドアウト評価、オフラインインストール、署名、SBOM、ライセンス、移行/回復試験。

- [ ] FR/NFRに未割当/未検証がない（MVP外FR-11は別計画を明記）。
- [ ] G00〜G05の承認証跡が揃っている。
- [ ] 指標と未対応/失敗件数を含む評価レポートがある。
- [ ] 高リスク既知欠陥なし。原本保護と隔離の負の試験に合格。
- [ ] WIKI出典・UI文言・対応表がエンジンの現版と一致。
- [ ] クラッシュ/更新失敗から回復できる。
- [ ] 配布物のハッシュ、署名、コミット、依存版を記録。
- [ ] PMとQA/セキュリティがG06を承認。

## 9. 今回の設計文書に対する検証

対象はdocs内のMarkdown。相対リンク先の存在、コードフェンス、JSON例のパース、PHASE 00〜07/G00〜G07の網羅、要求IDとAT/ST/PT参照、Base64例の正しさ、変更差分の空白問題を検査する。結果はPRに記録する。アプリ実装の試験合格と混同しない。
