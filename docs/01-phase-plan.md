# 01 — PHASE管理された実装設計図

## 1. 管理方式

各PHASEは `未着手 → 設計中 → 設計レビュー → 実装中 → 検証中 → 完了` で管理する。依存未達・重大問題は `保留` とし、再開時に直前状態へ戻す。本書作成は全PHASEの実装完了を意味しない。

各チケットに `ID / PHASE / 要求ID / owner / inputs / deliverables / tests / status / blockers / decision_log` を必須化。完了は担当者の自己申告ではなく、成果物・試験記録・レビュー署名が揃った時点。日数消化だけでは次に進まない。

推奨体制: PM/プロダクト、解析エンジニア、アプリエンジニア、UIデザイナー、QA/セキュリティ、知識編集者。兼任可能だが安全レビューと実装の承認者は分ける。

```text
00 ─→ 01 ─→ 02 ─→ 03 ──────────┐
 └─→ 04 記事執筆 ─→ 02/03連携 ─┼─→ 05 ─→ 06 ─→ MVP
                               │                 └─→ 07 個別拡張
06の試験設計・脅威分析は00から ──┘
```

## PHASE 00 — 要件・分類・安全境界

**狙い:** 「何を判定できるか」「何を戻せるか」を先に固定し、万能解除ツール化を防ぐ。

- 入口: ユーザーの目的、空リポジトリ、本設計案。
- 担当: PM（責任）、解析・セキュリティ・デザイン担当（レビュー）。
- P00-01: ユーザー像、FR/NFR、対象OS、言語と実ファイル規模をヒアリングする。
- P00-02: エンコード/圧縮/暗号/コード難読化を分け、方式IDと対応表を定義する。
- P00-03: 入力非実行・通信禁止・原本保全の脅威モデル、隔離の実証方法を決める。
- P00-04: 学習教材と評価用データを別集合にする。許諾・出典・生成方法・正解ラベルを記録する。
- P00-05: 「未知」「未対応」「未検出」「部分解析」と検証レベルの文言を固める。
- P00-06: 提示予定UIの受領条件、仮デザインの扱い、ブランド方向を合意する。
- 設計上の判断: Linux静的解析MVPを仮採用。Windows必須なら隔離スパイクを前倒しする。
- 成果物: 承認済み00/07、分類初版、ADR、評価コーパス仕様、画面マップ。
- **Gate G00:** 未決事項のうちOS/対象範囲/保存同意/隔離方式が決定済み。FR全件に受入試験を割当。制約をプロダクト責任者が承認。
- 失敗時: 目的が広すぎる場合は方式を減らす。危険試料を扱う隔離を確保できない場合は教材専用モードに縮退し、実ファイル対応を宣伝しない。
- 主な参照: [00](00-product-requirements.md)、[07](07-security.md)、[09](09-decisions-operations.md)。

## PHASE 01 — GUI・取込・隔離基盤

**狙い:** 解析アルゴリズムより先に「安全に読めて、止められて、壊れない」基盤を作る。

- 入口: G00、OS別隔離方式とファイルアクセス契約。
- 担当: アプリ担当（責任）、セキュリティ・UI担当。
- P01-01: サイドバー、ルーティング、空状態、ファイル選択、ドロップを構築。実解析と区別したモック状態を用意する。
- P01-02: ネイティブ選択トークン→安全なopen→同一ハンドルからスナップショットとSHA-256を作成。読み取り中変更を検知したら再取込を促す。
- P01-03: ジョブ制御、キュー、進捗イベント、キャンセル、上限監視、起動時の中断ジョブ整理を実装する。
- P01-04: 最小権限の子プロセス、通信/子起動/外部ファイル参照の禁止を実装し、自己診断を通す。
- P01-05: 保存同意、一時セッション、削除、ディスク不足、ロック/権限エラーを扱う。
- P01-06: ページ分割表示、制御文字の可視化、長いファイル名、空/巨大/破損ファイルを試験する。
- 設計上の判断: 同じOSプロセス内のタイムアウトは隔離ではない。UIへ生パスや任意コマンド権限を渡さない。
- 成果物: GUIシェル、取込サービス、Worker Supervisor、隔離自己診断、IPC契約v1。
- **Gate G01:** AT-01/02/14、ST-01/02/03/05が合格。原本のハッシュが不変。ワーカーを強制終了してもUI・DBが回復。隔離できないと解析が開始されない。
- 失敗時: ワーカー機能を停止し、WIKIだけ開ける状態を維持。処理速度のために隔離を外さない。
- 主な参照: [02](02-architecture.md)、[04](04-data-contracts.md)、[06](06-ui-ux.md)、[07](07-security.md)。

## PHASE 02 — 静的検知・種類の特定

**狙い:** ユーザーが追試できる根拠付き候補を返す。

- 入口: G01、分類ID、固定した評価セット、ルール契約。
- 担当: 解析担当（責任）、知識編集者・QA。
- P02-01: マジック・文字コード・部分範囲を判定し、解析可能/対象外を切り分ける。
- P02-02: 字種分布、長い文字列、局所エントロピー、構文特徴、minifyの指標を抽出する。
- P02-03: Base64/Base64url/Base16、文脈付きescape、gzip、JS構造について検知器を分離する。
- P02-04: 根拠の重複をまとめ、代替仮説と反証を記録する。名前やエントロピーだけで断定しない。
- P02-05: 種類スコアと難読化兆候を別集計し、未知・未対応・未検出を表示する。
- P02-06: 検証用の小さなデコードを許可リスト内の隔離器で行う。出力は試験用一時データでありユーザー承認済み解除とは扱わない。
- P02-07: 誤検知例を教材化する。例: 正常なJWT形式の文字列、minify済み配布JS、画像や圧縮データの高エントロピー。
- 成果物: ルールパックv1、Feature/Finding出力、根拠ビュー、評価レポート。
- **Gate G02:** AT-03/04/05を合格。08の暫定精度基準を方式別に満たす。解析済み範囲と除外ルールを表示し、通常圧縮を自動的に難読化陽性にしない。
- 失敗時: 不安定な検知器は実験ラベルで別表示、または無効化。評価セットに合わせて根拠なくスコアを上げない。
- 主な参照: [03](03-analysis-pipeline.md)、[04](04-data-contracts.md)、[08](08-quality-validation.md)。

## PHASE 03 — 解除・可読化・検証

**狙い:** 理由を確認してから変換し、何が保存・変更されたか説明できるようにする。

- 入口: G02、方式ごとの前提条件・逆変換・検証仕様。
- 担当: 解析担当（責任）、アプリ・QA・セキュリティ担当。
- P03-01: Base系、文脈付きescape、gzip、JS整形、純粋リテラル連結のアダプターを実装する。
- P03-02: Plan→Preview→Approve→Apply→Validateを分離。入力/アダプター/パラメータ/上限が変わったら承認を失効させる。
- P03-03: 変換を不変の派生Artifactとして記録。親、方式、ハッシュ、版、範囲対応を保存する。
- P03-04: 多層候補をDAGで保持し、最大深度・試行回数・累積出力・重複ハッシュで停止する。
- P03-05: 逆変換、構文再解析、限定規則の前提検証を行う。任意コードを実行する等価性テストは禁止する。
- P03-06: 複数候補、部分成功、変化なし、意味未検証、入力不正を個別表示する。
- P03-07: テキスト/Hex/AST差分、未解除層、履歴の分岐・戻る操作を実装する。
- 成果物: 安全な変換アダプター、検証器、差分モデル、変換DAG。
- **Gate G03:** AT-06/07/08/09、ST-04/07合格。正解既知の可逆教材は期待バイト列と完全一致。対応外構文の勝手な書換えなし。全出力に検証レベルと未解決事項を付与。
- 失敗時: 検証不合格の出力は隔離された失敗候補として残すだけで、推奨出力・自動チェーン入力にはしない。
- 主な参照: [03](03-analysis-pipeline.md)、[04](04-data-contracts.md)、[07](07-security.md)。

## PHASE 04 — WIKI・歴史・体系・教材

**狙い:** 単なるヘルプではなく、原理と歴史を辿れる学習基盤を提供する。

- 入口: G00で記事執筆開始可能。最終結合にはG02/G03が必要。
- 担当: 知識編集者（責任）、解析・UI担当。
- P04-01: 分類、年代、言語、可逆性、理解難度を独立した検索軸として設計する。
- P04-02: 出典付き年表と方式記事12本以上を作成し、事実/推定/未確認を区別する。
- P04-03: 記事に概要、歴史、原理、前後例、検知根拠、誤検知、解除限界、関連記事を必須化する。
- P04-04: オフラインMarkdown/JSONのスキーマ、日英検索索引、用語辞典、改訂履歴を作る。
- P04-05: technique_idでFinding/変換と記事を接続。記事から戻っても元の候補・スクロール・選択領域を保持する。
- P04-06: 自作の無害な教材を別セッションで開き、クイズと期待結果を表示する。
- P04-07: 文章・画像のライセンスと引用量を点検。外部画像やスクリプトの自動取得を禁止する。
- 成果物: WIKIパックv1、年表、用語辞典、無害教材、検索索引、出典台帳。
- **Gate G04:** AT-10/11合格。記事必須項目・リンク整合性100%。年表の全項目に出典/年精度。WIKI掲載とエンジン対応を別バッジで表示。オフラインで全教材を読める。
- 失敗時: 出典確認できない歴史上の断定を削る/保留。記事の存在を理由にエンジン対応済みと表示しない。
- 主な参照: [05](05-wiki-knowledge.md)、[06](06-ui-ux.md)。

## PHASE 05 — 統合GUI・研究ワークフロー

**狙い:** 部品の集合から、一貫した研究体験へ統合する。

- 入口: G03/G04、提示UIまたは代替デザインの明示承認。
- 担当: UI/アプリ担当（責任）、解析・QA担当。
- P05-01: デザイントークンと全画面を最終化。SFらしさと長時間の読解性を両立する。
- P05-02: Overview/Evidence/Transform/Compare/WIKIの状態を共有し、同じファイル/派生物を見ていることを明示する。
- P05-03: 解析プリセット、承認ダイアログ、中止、進捗、エラー回復を統一する。
- P05-04: セッションの保存・再開・分岐・削除、原本の含有有無と版違いの警告を実装する。
- P05-05: JSONとスクリプトなしHTMLのレポート、機密情報の削除/マスキングプレビューを実装する。
- P05-06: 1366×768以上の作業画面、200%ズーム、キーボード、色覚差、reduce-motionを検証する。
- P05-07: 初学者/熟練者を含むユーザビリティ試験で「未検出≠安全」が伝わるか確認する。
- 成果物: 統合MVP候補、承認済みUI仕様、E2Eテスト、レポート仕様。
- **Gate G05:** AT-01〜14のE2E合格。主要導線がキーボードのみで完了。書き出し前に秘密/原本の含有を確認でき、未対応を成功と誤表示しない。
- 失敗時: 装飾よりタスク完了を優先。UI資料未到着かつ代替デザインの明示承認もない場合はこのゲートを保留し、最終デザイン承認を捏造しない。
- 主な参照: [06](06-ui-ux.md)、[04](04-data-contracts.md)。

## PHASE 06 — 品質・安全性・配布

**狙い:** 根拠のある限定公開MVPとして出荷する。

- 入口: G05、署名・配布先・ライセンス方針。試験準備自体は00から行う。
- 担当: QA/セキュリティ（責任）、全担当。
- P06-01: 固定ホールドアウトによる方式別評価、誤検知分析、再現性試験を実施する。
- P06-02: 破損入力fuzz、巨大構文、展開爆弾、パストラバーサル、UI注入、ワーカー侵害想定を試験する。
- P06-03: 参照端末でp50/p95、最大RSS、停止時間、長時間稼働を測定する。
- P06-04: 依存版固定、SBOM、署名、WIKI/ルールの整合性、オフライン起動を検証する。
- P06-05: 更新失敗・破損DB・ディスク不足・中断からの回復を試験。データ移行のバックアップ方針を実装する。
- P06-06: 対応/非対応一覧、既知制約、研究用途の注意、問い合わせ・訂正手順を配布物に含める。
- 成果物: リリース候補、試験証跡、脅威モデル更新、配布/回復手順、出荷判定記録。
- **Gate G06:** 08の基準すべて達成。既知Critical/High安全問題ゼロ、MVP対象FR/NFRの未検証項目ゼロ（FR-11は07の個別ゲート）、ライセンス確認済み。PMとQA/セキュリティが出荷承認。
- 失敗時: 出荷を止め、危険アダプターの除外やスコープ縮小後に再評価する。既知の不合格を免責文だけで通さない。
- 主な参照: [07](07-security.md)、[08](08-quality-validation.md)、[09](09-decisions-operations.md)。

## PHASE 07 — 高度解析・対応拡張（別ロードマップ）

**狙い:** MVPの安全・証拠・再現性を維持しつつ対応領域を増やす。

- 入口: G06、利用実績、拡張ごとの要求・予算・脅威レビュー。
- 担当: 解析リード（責任）、拡張ごとの担当者。
- P07-A: PE/ELF/Mach-Oのセクション解析、既知packerの版限定特定、UPX等の静的unpack。成功と実行可能性を別検証する。
- P07-B: JS文字列テーブル、制約付き定数伝播、CFG表示。副作用/動的参照がある箇所は変換しない。
- P07-C: Python/PowerShell/Java/.NETのパーサ単位の静的対応。VM起動やimportは行わない。
- P07-D: 署名付きルールパック/外部アダプター。UIへのコード注入を許さず能力権限を個別審査する。
- P07-E: バッチ・CLI・Windows/macOSへの展開。各OSで隔離試験をやり直す。
- P07-F: 動的解析は単なるチェックボックスで追加しない。別製品境界/使い捨てVM/スナップショット/ネットワーク閉鎖/追加同意/専用審査を必要とする独立検討課題。実装承認は本書に含めない。
- 成果物: 拡張ごとの対応表、アダプター契約、独立ベンチマーク、WIKI更新。
- **Gate G07（拡張ごと）:** MVP回帰試験に合格し、追加対象の精度・意味保存・隔離を評価。未知形式で安全停止し、明示的に有効化できる。
- 失敗時: 拡張だけ無効化。MVPの既存結果/履歴を壊さない。

## 2. 規模の目安と順序

暫定工数はP00:1〜2、P01:3〜5、P02:4〜6、P03:4〜6、P04:3〜5、P05:3〜5、P06:3〜5人週、合計21〜34人週。07は別見積。これは実測や納期ではなく、単一OS・限定方式での計画仮説である。教材・UIが並行できても統合/安全レビューの依存はなくならない。G00後に再見積し、各ゲートで残量を更新する。

## 3. 変更とレビュー

- PHASE完了後の対象追加は、要求・脅威・テスト・WIKI・UIへの差分を評価する。
- Gate記録: `phase / build_commit / evidence_links / metrics / outstanding_items / approvers / date`。
- Must未達は完了不可。Shouldを保留する場合は担当者・期限・利用者影響を明示する。
- 主要成果物はPRレビューし、将来実装と同じリポジトリで版管理する。詳細は[09](09-decisions-operations.md)。
