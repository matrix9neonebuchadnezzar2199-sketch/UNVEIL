# 03 — 検知・特定・解除パイプライン

## 1. 解析結果を四つの軸に分離する

| 軸 | 値 | 意味 |
|---|---|---|
| coverage.status | full / partial / unsupported | 設定された対応検査をどこまで実施したか |
| assessment | indicators_present / no_indicators / inconclusive | 対応範囲内の難読化兆候の評価 |
| identification | confirmed / probable / possible / unknown | 方式候補の証拠強度 |
| transformability | supported / partial / needs_parameters / unsupported | 現版の解除支援範囲 |

`full`は「すべての未知方式を調べた」の意味ではない。どのルールをどの範囲に実行したかとセットである。`confirmed`はBase64等の形式の成立を示せても、その意図が難読化や攻撃であることは示さない。処理の成功/失敗はさらに別のJob状態である。

## 2. パイプライン

```text
取込 → 形式/文字コード → coverage計画 → 特徴抽出 → 検知器
     → 候補の統合/代替説明 → 根拠付き結果 → 変換計画
     → bounded preview → 利用者の承認 → 変換 → 検証
     → 派生Artifact確定 → 再検知/比較 → レポート
```

### 2.1 Probe・領域抽出

- ファイルはバイト列として保持し、表示の文字コードを別属性にする。
- UTF-8はstrict検査、UTF-16はBOM必須をMVPの自動認識条件とする。不正バイトを置換してから解析しない。
- BOM、改行、Unicode、JS escapeの元バイト位置を保持する。正規化表示と原本を混同しない。
- JSは成功したASTから文字列リテラル範囲を抽出。解析失敗時は汎用テキスト特徴へ下げ、AST未解析と明示する。
- 非JSでは上限付き字句候補抽出を使用。HTML/PDF/Office/実行ファイルをレンダリング/起動しない。
- 10 MiBを超える入力の粗い分布は先頭・中央・末尾各64 KiBを重複除去して調べ、実際のバイト範囲をcoverageに記録する。これは内部形式の解析を意味しない。

### 2.2 特徴

- 長さ、可視文字率、字種ヒストグラム、行長、識別子長、文字列リテラル長。
- 局所エントロピー `H = -Σ p(b) log2 p(b)`、単位bits/byte、範囲0〜8。窓4096 bytes、歩幅2048 bytesを暫定値とし、小さい窓では推定が不安定と注記する。
- 構文ノード種別、純粋な連結式の深さ、escape比率、動的評価を示す構文の存在。構文の存在だけで実行されるとは推論しない。
- 圧縮・画像・暗号化はいずれも高エントロピーになり得る。エントロピー単独では難読化陽性にも暗号方式確定にもしない。
- 検出領域は最大1000候補/ジョブ。超過は切り捨て数と未検査領域を表示し、coverageをpartialにする。

## 3. MVP検知器・変換器仕様

| technique_id | 候補検出 | 方式特定の根拠/反証 | 対応操作と主な限界 |
|---|---|---|---|
| enc.base64 | 字種・長さ・padding・文脈 | strict decodeと再encode一致。普通の単語/IDも候補になる | 選択範囲をbytesへ。秘密性はない |
| enc.base64url | URL-safe字種、無paddingも別プロファイル | `-`/`_`等がなければ通常版との曖昧さを残す | padding補完は承認済みプロファイルでのみ |
| enc.base16 | 偶数長・hex字種・文脈 | decode/reencode、大文字小文字プロファイル | ハッシュ表記の可能性を併記 |
| enc.percent | `%HH`構造、選択文脈 | バイト列として妥当か。URL/formの差 | `+`を勝手に空白へ変えない |
| enc.js-escape | JS文字列内の`\xHH`/`\uHHHH`等 | パーサの言語版と文字列の意味 | 任意本文にJS規則を当てない |
| compression.gzip | マジック/ヘッダ構造 | 上限付き展開とCRC/ISIZE検証 | 名前を無視し仮想出力。多memberはMVP対象外 |
| layout.minify | 行長/空白比/識別子の分布 | 通常のビルド成果物でも同じ | 整形のみ、元の命名は戻せない |
| data.literal-concat | 純粋な文字列リテラル同士の連結 | AST前提条件を満たすか | 限定式を置換。外部呼出しや変数参照は対象外 |
| data.string-table | 配列参照/復元関数に似た構造 | MVPは一般的構造兆候のみ。製品特定しない | 自動復元は07、MVPは記事案内 |
| control.dynamic-eval | `eval`等の関連構文 | シャドーイング等の代替説明 | 実行せず、対象特定は保留 |

Base64は通常テキスト全域の短い一致を大量検出しやすい。汎用スキャンは16文字以上を候補の初期下限とする。利用者の明示選択/教材は短い値も扱い、低文脈の一致を難読化陽性にしない。実際のしきい値は校正データで調整し、版を記録する。

Gzipは連結member、末尾余剰、破損CRCを検出したら自動確定しない。ヘッダの元ファイル名やパスへ書き出さない。CRCが正しくても悪意の有無やプログラム等価性は証明できない。

## 4. 証拠の統合と信頼度

MVPでは確率モデルを装わず、説明可能なルール方式を採る。

- `score.value`は0〜100の**ルール一致度**。UIに「成功確率95%」のように表示しない。
- 暫定共通配点: 字種等の弱い一致0〜10、構造0〜30、独立した再変換/構文整合性0〜40、文脈0〜20、矛盾0〜60減点、合計を0〜100へclamp。方式ごとに適用項目・最大値をルール定義に固定する。
- 同じ情報源の重複証拠はグループ上限で抑える。字種regexを三つ当てても三つの独立根拠にならない。
- confirmed: 決定的な形式検査と整合性検証に合格し、スコア80以上、解消できない競合候補なし。
- probable: 60以上かつ異なる証拠グループ二つ以上。possible: 30以上、または利用者が明示選択した弱い候補。その他はunknown。
- 複数方式が同じバイト列に成立する場合は候補を残し、confirmedを避ける。候補集合を表示する。
- ファイルの難読化兆候は別規則。文字列隠蔽と復元利用の構造などの文脈を必要とする。エンコード/圧縮の成立だけならassessmentはinconclusiveまたはno_indicators（実施範囲に依存）。
- ユーザー注記は観測結果を上書きしない。研究者の判断として別記録し、ルール更新時にも履歴を保つ。

assessmentの集約は次の規則とする: 文脈付きの難読化兆候ルールを満たすFindingがあればindicators_present。該当兆候がなく、実施できた検査範囲に未解消の候補がなければno_indicators。曖昧な候補/矛盾/方式不明があればinconclusive。基本メタデータしか調べていない未対応形式は必ずinconclusiveとする。partialでのno_indicatorsは実施範囲だけの結論であり、除外範囲を同じ画面に示す。通常minify/通常圧縮だけでは陽性にしない。

UIにはスコア、検査内容、観測位置、反証、未適用検査を開示する。未知判定を避けるために最上位候補を強制選択しない。

## 5. 変換契約と承認

Planには入力Artifactハッシュ、範囲、方式ID、アダプター版/ハッシュ、設定、前提、最大出力、損失性、検証器を含める。計画ハッシュに対する承認トークンを発行し、パラメータや対象が変われば再承認。

- 検知中probe: 小さい範囲の形式確認。ユーザー用成果物を確定しない。
- Preview: 利用者の「プレビュー」操作で、同じ隔離アダプターを上限付き実行。未承認候補として一時保持する。
- Apply: 承認時に入力/計画/候補ハッシュを照合。候補を確定するか、同じ条件で再実行し一致を検証する。
- 部分範囲のデコードは独立Artifactに抽出する。MVPは任意ファイル内部へ復号bytesを直接差し戻さない。JS書換えのみASTの妥当性を確認して全体派生物を生成する。
- Adapterの呼出しは固定関数/固定引数schema。シェル文字列や汎用evalを生成しない。
- 変換後も成果物は非信頼。OS既定アプリで自動的に開かない。

### JS意味保存の限定

MVPの書換えは純粋な文字列リテラル同士の`+`に限定する。ToPrimitive、getter、関数、外部変数、テンプレートtag、数値混在は対象外。directive prologueに新たな`"use strict"`を生成し得る位置は拒否する。source text観測（Function.prototype.toString等）、行番号、スタックトレースの一致は保証しない。

整形はコメント・文字列値・正規表現・ASI等を保持できるパーサ/プリンタを採用し、前後ASTとdirectiveを比較する。構文解析できない断片を「直して実行可能」にする機能は含めない。

## 6. 多層・分岐の探索

既定は1ステップごとの手動承認。自動チェーンは利用者が方式の許可リストと予算を承認した場合だけ有効。

```text
root
 ├─ decode A ─→ gzip展開 ─→ テキスト (推奨候補)
 └─ decode B ─→ 不正な構造 (棄却)
```

DAGのノードはArtifact、辺はTransformStep。別の変換経路で同じbytesが得られても辺の由来は保持する。

停止条件: 5段、全分岐20試行、累計出力100 MiB、ジョブ60秒、単一変換10秒、重複ハッシュ、変化なし、検証失敗、曖昧な次候補、対応アダプターなし、中止。

重複判定キーはbytesハッシュ＋方式/パラメータ。probeは解析Jobの予算に、preview/apply/子変換は同一Planの共有予算台帳に出力bytes・稼働時間を計上する。Planの共有上限も60秒/100 MiBとし、承認待ちの利用者時間は除外する。同じPlanの削除/中止/再送で台帳をリセットしない。別の明示的な再解析/新Planは新予算を持つが、Sessionの保存/同時実行上限（07）は常に共有する。高い変換適合度の順に安定ソートするが、曖昧な候補は自動選択せず止める。

## 7. 検証と成功の意味

| validation.checks[].kind | 検査 | 言ってよいこと | 言ってはならないこと |
|---|---|---|---|
| none | 未検証/検証不能 | 候補出力を生成 | 解除成功 |
| round_trip | 逆変換で入力範囲に一致 | この表現変換の可逆性を確認 | 元の作者意図を復元 |
| structural | パーサ/圧縮整合性等 | 構造検証に合格 | 意味等価を証明 |
| rule_checked | 限定書換え前提と前後構造 | 規則の適用条件を検証 | 全実行環境で同じ挙動 |
| fixture_exact | 正解既知の教材と一致 | 当該教材の期待bytesと一致 | 任意入力でも正しい |

これらは単純な強さの序列ではない。`checks[]`として併記し、検証できた性質を表示する。base16大小文字等を正規化した照合では、正規化規則を保存して「バイト完全一致」と区別する。

変換結果は `transformed / partial / no_change / rejected / failed`。`transformed`は対応操作を実施したという意味で、ファイル全体の難読化消失を示さない。未解除のFinding一覧と意味保存上の限界を必ず付ける。

## 8. 無害な追試例

1. 選択範囲 `SGVsbG8sIFVOVkVJTCE=` をBase64として検査する。
2. strict decodeにより `Hello, UNVEIL!` のUTF-8 bytesを得る。
3. 再encodeが一致する。この値はBase64urlとも両立するため、自動特定はprobableとし、候補を併記する。選択したBase64規則でのround_trip合格と、元の方式/難読化意図の確定を区別する。
4. 別Artifactへ確定し、round_tripを記録。元文字列を書き換えない。
5. 利用者はenc.base64のWIKIで「エンコードと暗号の違い」を確認する。

複合例は自作の `Base64(gzip(Hello, UNVEIL!))` を用い、mtime固定で教材生成する。各層のハッシュと順序を正解データに保持する。未知の中身を表示可能な文字列にできても、無害化したとは説明しない。
